# ТЗ: image-to-vector

Расширения к движку VTracer 1.0, закрывающие то, что он не умеет:
альфа-канал, градиенты и геометрическую регуляризацию.

> **Эта версия ТЗ заменяет предыдущую.** Первая редакция была написана против
> VTracer 0.6 и предлагала строить пре/постобработку вокруг движка. VTracer
> 1.0.0-alpha.3 (1 августа 2026) реализовал бо́льшую часть того списка внутри
> себя. Раздел §0 фиксирует, что именно устарело и почему.

---

## 0. Что уже сделано апстримом (и потому вычеркнуто из ТЗ)

Проверено по README и исходникам `visioncortex/vtracer@1.0.0-alpha.3`:

| Было в первой редакции ТЗ | Что в VTracer 1.0 | Статус |
|---|---|---|
| Слияние близких цветов по ΔE | `--palette` / `--palette-file`, снап к ближайшему в **OKLab** | вычеркнуто |
| Квантование палитры | `--max-colors`, `colorfit::AutoQuantize` | вычеркнуто |
| Упрощение путей (RDP) | `--simplify <tol>`: пере-подгонка Schneider'ом, «fewest cubics within tolerance», обычно вдвое меньше файл | вычеркнуто (их решение лучше RDP) |
| Прогон через SVGO | `--optimize 0\|1\|2`, `optimize::{QuantizePass, CleanupPass}` | вычеркнуто |
| Адаптивный порог для сканов | `--adaptive`, Bradley–Roth, `--adaptive-window`, `--adaptive-t` | вычеркнуто |
| Устранение швов/перекрытий между слоями (планировалось как главный вклад) | `--hierarchical cutout` — настоящая бесшовная мозаика с общими границами; общая граница упрощается один раз для обеих граней | **вычеркнуто — апстрим сделал именно это** |
| Умная сегментация вместо обрезки битов | `--clustering watershed` — иерархический watershed по пиксельному графу (Cousty et al., TPAMI 2009) | вычеркнуто |
| A/B-сравнение и инспектор узлов | есть в их десктопном приложении 1.0 | вычеркнуто как «фича», остаётся как часть бенчмарка (§7) |

**Вывод:** обёртка вокруг движка больше не имеет смысла. Смысл имеет только то,
чего в движке нет.

## 1. Что осталось нерешённым

1. **Альфа-канал.** Во всём наборе опций 1.0 нет ни одного упоминания
   прозрачности: ни порога альфы, ни борьбы с цветной бахромой, ни учёта
   покрытия сглаженных пикселей. Пайплайн работает по жёстко расклассифицированным
   пиксельным регионам. Прозрачный PNG с антиалиасингом по краю — исходная
   задача проекта — остаётся необработанным случаем.
2. **Градиенты.** В `ir::Paint` буквально написано:
   `/// Only solid colors are supported today; the enum leaves room for
   gradients and patterns later.` Единственный вариант — `Solid(Color)`.
   Плавный переход раскладывается в N плоских слоёв вместо одного
   `<linearGradient>`.
3. **Геометрическая регуляризация.** Окружность остаётся набором кубик, прямая
   слегка волнится, скруглённый прямоугольник не распознаётся, зеркальная
   симметрия логотипа не соблюдается, срезанный антиалиасингом острый угол не
   восстанавливается. Ничего этого в 1.0 нет.
4. **Браузер и батч.** Приложение с A/B-компаратором — десктопное (Tauri).
   npm-пакет `@visioncortex/vtracer` заявлен как **Node.js** WASM-сборка.
   Бесплатного браузерного инструмента на движке 1.0, с батчем и
   переносимыми пресетами, нет.

## 2. Точки расширения (проверены по исходникам)

VTracer 1.0 — это явно framework с публичными трейтами. Форк не нужен,
кроме одного случая (см. §4).

```rust
// frontend.rs — сегментация растра в слои
pub trait Frontend { fn segment(&self, img: &ColorImage) -> Result<Segmentation, Error>; }

// colorfit.rs — переписывание заливок сегментации на месте
pub trait ColorFitter { fn fit(&self, seg: &mut Segmentation); }

// simplify.rs — геометрический проход между подгонкой кривых и композицией
pub trait CurvePass {
    fn open(&self, geom: FittedGeom) -> FittedGeom;  // концы закреплены
    fn ring(&self, geom: FittedGeom) -> FittedGeom;  // кольцо остаётся замкнутым
}

// fitter.rs — подгонка кривых
pub trait CurveFitter { /* PixelFitter | PolygonFitter | SplineFitter */ }

// optimize.rs — проходы оптимизации вывода
pub trait OptimizerPass { /* QuantizePass | CleanupPass */ }
```

Плюс расщепляемый пайплайн — сегментация кешируется, доводка перезапускается:

```rust
let pipeline = cfg.build()?;
let seg = pipeline.segment(&img)?;   // дорогая часть
let doc = pipeline.finish(&seg)?;    // быстрая, гоняется при каждой правке параметра
```

Полезно и то, что уже есть: `mosaic::LabelMap::from_segmentation(&seg)` даёт
карту меток регионов и `merge_similar(max_diff)` — готовая машинерия
смежности регионов.

**Контракт `CurvePass` важен:** «endpoints pinned, mosaic junction nodes must
not move». Значит наш геометрический проход автоматически не ломает
бесшовность мозаики — это снимает самую опасную часть задачи §5.

## 3. Модуль A — альфа-ориентированный фронтенд *(приоритет 1)*

`struct AlphaFrontend` реализует `Frontend`. Решает исходную задачу.

**Проблема.** У сглаженного края прозрачного PNG пиксели имеют `0 < a < 255`, а
их RGB часто содержит примесь фона (или мусор при непремультиплированной
альфе). Кластеризация по цвету видит в этой кайме отдельные цвета и делает из
них тонкие паразитные регионы — это и есть «ореол».

**Решение.**

1. **Восстановление цвета в кайме.** Для пикселей с `0 < a < 255` цвет берётся
   не как есть, а экстраполируется из ближайших непрозрачных соседей
   (расширение цвета наружу по расстоянию). Убирает примесь фона до того, как
   начнётся кластеризация.
2. **Альфа как поле покрытия, а не как цвет.** Значение `a` трактуется как
   доля покрытия пикселя фигурой. Внешний контур строится не по бинарной
   маске, а по изолинии `a = 0.5` поля покрытия, с **линейной интерполяцией
   между соседними пикселями** (marching squares по субпиксельным
   пересечениям). Это даёт положение края точнее пиксельной сетки — то, чего
   бинарный пайплайн дать не может в принципе.
3. **Восстановление острых углов.** Там, где две почти прямые стороны сходятся
   и антиалиасинг скруглил вершину, угол восстанавливается пересечением
   продолжений сторон, если ошибка относительно поля покрытия при этом не
   растёт.
4. **Порог и деспекл** по альфе — тривиальная часть, но должна быть.

Внутри контура сегментация делегируется штатному
`ColorClusterFrontend`/watershed — своё изобретать не нужно, только альфа-часть.

**Приёмка:** на корпусе прозрачных логотипов ореол отсутствует при зуме 800%;
средняя ошибка положения контура относительно эталона меньше, чем у ванильного
VTracer на том же входе (метрика — §7).

## 4. Модуль B — градиентный `ColorFitter` *(приоритет 3, требует апстрима)*

**Ограничение, определяющее подход:** `Paint` — enum из чужого крейта с
единственным вариантом `Solid(Color)`. Добавить `Gradient` извне невозможно.
Значит модуль B — это **не внешний плагин, а форк или PR в апстрим**.
Комментарий в их коде («leaves room for gradients and patterns later») говорит,
что PR был бы уместен.

**Суть.** В сегментации найти группы смежных регионов, чьи средние цвета лежат
на прямой в OKLab и монотонно меняются вдоль пространственного направления →
заменить группу одним регионом с `Paint::Linear{ x1,y1,x2,y2, stops }`.
Аналогично радиальный случай. Порог принятия — по ошибке восстановления
относительно оригинала.

**Выигрыш:** один путь с градиентом вместо 12 полос — заметно меньше файл и
принципиально лучше редактируемость.

**Решение о запуске принимать только после A и C.** Требует форка, значит
требует поддержки синхронизации с апстримом.

## 5. Модуль C — геометрическая регуляризация `CurvePass` *(приоритет 2)*

`struct RegularizePass` реализует `CurvePass`. Плагин, форк не нужен.

Для каждого контура, в пределах допуска `tolerance` (px):

1. **Примитивы.** Замкнутое кольцо, ложащееся на окружность / эллипс /
   прямоугольник / скруглённый прямоугольник — заменяется идеальным примитивом.
2. **Прямые.** Последовательность кубик, ложащаяся на прямую — схлопывается в
   отрезок; почти-горизонтали и почти-вертикали (в пределах ~0.5°) снапятся к
   осям.
3. **Симметрия.** Поиск оси зеркальной симметрии контура; при совпадении в
   пределах допуска половины усредняются и отражаются — логотип перестаёт быть
   «почти симметричным».
4. **Согласование радиусов.** Близкие по величине скругления в пределах одной
   фигуры приводятся к общему значению.

Всё выключено по умолчанию, включается пресетом `logo`. Контракт трейта
(закреплённые концы, замкнутость колец) соблюдать строго — иначе ломается
бесшовная мозаика.

**Приёмка:** на корпусе логотипов число узлов падает минимум на 25%
относительно `--simplify` в одиночку при не худшей ошибке восстановления.

## 6. Обвязка

Осознанно скромная — движок и его десктопное приложение уже хороши.

- **Браузерное приложение**: drag-n-drop, панель параметров (включая наши A/C),
  сравнение с оригиналом (шторка + diff), скачивание. Работает локально,
  ничего не грузится в сеть.
- **Батч**: N файлов одним профилем → zip + CSV-отчёт.
- **Профиль** — сериализуемый JSON, общий для веб-приложения, CLI и бенчмарка.

Это ценно только как бесплатная браузерная точка входа с нашими модулями.
Если модули A/C не взлетят, обвязку делать не стоит вовсе.

## 7. Бенчмарк — обязательная часть, не опция

Цель проекта сформулирована как «лучше, чем VTracer», значит нужен измеритель.
Без него работа превращается в подбор параметров на глаз.

**Корпус:** ≥40 изображений, зафиксированы в репозитории, по группам:
прозрачные логотипы с антиалиасингом, плоские иконки, штриховые сканы,
градиентные логотипы, пиксель-арт, фото-постеры.

**Метрики на каждый прогон:**

- **Ошибка восстановления:** отрисовать выходной SVG (resvg) с 2× суперсэмплингом,
  сравнить с оригиналом по RGBA с учётом альфы — среднее и 99-й перцентиль;
  плюс SSIM.
- **Число узлов**, число путей, число цветов.
- **Размер SVG** после `--optimize 2` и gzip.
- **Время** сегментации и доводки отдельно.

**Правило:** каждый модуль сравнивается с ванильным VTracer 1.0 на тех же
настройках. Улучшение считается состоявшимся, только если ошибка не выросла,
а целевая метрика (ореол / узлы / размер) улучшилась. Результаты — таблицей в
README, обновляются в CI.

## 8. Стек и репозиторий

- **Ядро — Rust.** Плагины реализуют трейты `vtracer`, значит другого варианта
  нет. `cargo add vtracer@1.0.0-alpha.3`. Версию зафиксировать точно: апстрим в
  alpha, API может поехать.
- `crates/i2v-core` — модули A и C, без привязки к UI.
- `crates/i2v-cli` — CLI поверх ядра.
- `crates/i2v-bench` — корпус, метрики, генерация таблицы.
- `web/` — WASM-сборка ядра (`wasm-pack build --target web`) + фронтенд на
  TypeScript. Собирать **свою** WASM-сборку: npm-пакет апстрима заявлен как
  Node.js-сборка и в браузере может не завестись.
- Тесты: обязательно на восстановление цвета в кайме, на marching squares с
  интерполяцией, на распознавание примитивов, на сохранение контракта `CurvePass`.
- CI: `cargo fmt`, `clippy -D warnings`, `cargo test`, прогон бенчмарка.
- Лицензия MIT (совместима с VTracer MIT/Apache-2.0). **Potrace (GPL) не тянуть.**

## 10. Задачи верификации (до кода)

1. Собирается ли `vtracer@1.0.0-alpha.3` под `wasm32-unknown-unknown` и какого
   размера выходит WASM после brotli.
2. Полные сигнатуры `Segmentation`, `Layer`, `RegionMask`, `FittedGeom`,
   `SubPath`, `PathCmd` — от них зависит реализуемость A и C в заявленном виде.
3. Как `Config` подключает пользовательские `Frontend` / `CurvePass` — через
   поля `Config`, через `Session`, или только через ручную сборку `Pipeline`.
   Если публичного способа подставить свой трейт нет — это меняет план
   (тогда A и C тоже уходят в форк, как B).
4. Что именно ванильный пайплайн делает с альфой сейчас (игнорирует,
   премультиплицирует, отбрасывает?) — от этого зависит объём модуля A.
5. Стабильность API: насколько alpha.1 → alpha.3 ломал сигнатуры.
