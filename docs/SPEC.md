# ТЗ: image-to-vector

Расширения к движку VTracer 1.0, закрывающие то, что он не умеет: альфа-канал
и геометрическую регуляризацию. Rust, консоль/десктоп — не веб (см. §0.1).

> Третья редакция. Первая была написана против VTracer 0.6 и предлагала
> строить обвязку вокруг движка (устарела — VTracer 1.0 сделал большую часть
> сама, см. историю в git). Вторая перенесла фокус на расширение через
> публичные трейты VTracer 1.0 и **уже частично реализована** — код в
> `crates/` ниже не черновик, он собирается, тестируется и подтверждает
> заявленное. Эта редакция фиксирует, что именно проверено и построено, и
> убирает браузер/WASM по прямому решению заказчика.

---

## 0. Что изменилось в этой редакции

### 0.1 Не веб

Заказчик подтвердил: браузер не нужен, можно консоль или десктоп, запуск
локально. Это снимает весь пункт «своя WASM-сборка + TypeScript-фронтенд» —
самую тяжёлую и наименее ценную часть предыдущего плана. Ядро — чистый Rust,
без DOM-зависимостей. Веб остаётся технически достижимым (см. §0.3), но не
строится, пока не попросят отдельно.

### 0.2 M0 пройден — вот что подтвердилось

Все блокирующие вопросы прошлой редакции проверены **кодом, а не чтением
доков**: собран рабочий Cargo workspace (`crates/i2v-core`, `i2v-cli`,
`i2v-bench`), зависящий от `vtracer = "=1.0.0-alpha.3"`, он компилируется,
проходит `clippy` и тесты, и CLI на нём реально превращает PNG в SVG.

1. **Прямая сборка `Pipeline` без форка — подтверждено кодом.**
   `vtracer::Pipeline` — обычная структура с публичными полями
   (`pub frontend: Box<dyn Frontend>`, `pub curve_passes: Vec<Box<dyn
   CurvePass>>`, …), и в её doc-комментарии буквально написано: «Build one
   with `Config::build`, or construct it directly for full control». В
   `crates/i2v-core/src/lib.rs` есть `alpha_pipeline()`, который берёт
   `Pipeline` из `cfg.build()` и подменяет `.frontend` на свой —
   компилируется, тест `alpha_pipeline_builds_and_traces_without_forking_vtracer`
   проходит. Вопрос закрыт: A и C — плагины, не форк.
2. **`BinaryImage`/`RegionMask` полностью публичны и собираются вручную.**
   `BinaryImage::new_w_h(w, h)` + `set_pixel(x, y, bool)` — оба `pub`,
   `pixels: BitVec` тоже `pub`. Значит наращивание разрешения маски (для
   субпиксельной точности, см. §3) технически ничем не ограничено.
3. **Реальный масштаб задачи с альфой — точнее, чем предполагалось.**
   Прочитан `frontend/keying.rs` (единственное место в движке, где вообще
   встречается слово «alpha»/чтение альфа-байта). Там есть эвристика: если
   ≥20% пикселей в пяти выборочных строках имеют `a == 0`, картинка целиком
   считается «существенно прозрачной», и такие пиксели перекрашиваются в
   служебный цвет-ключ перед кластеризацией. Это:
   - **приватный модуль** (`mod keying;`, не `pub mod`) — снаружи крейта
     недоступен, повторить его напрямую нельзя, только переписать своё;
   - работает только с `a == 0` (полностью прозрачные);
   - **не работает вообще** для промежуточной прозрачности `0 < a < 255` —
     ровно та самая антиалиасинговая кайма, из-за которой появляется ореол.
   Все встроенные `Frontend` (`ColorClusterFrontend`, `BinaryFrontend`,
   `WatershedFrontend`) кластеризуют только по RGB — альфа-байт, который
   физически есть в `ColorImage.pixels` (RGBA-буфер), при сегментации не
   читается никем, кроме этой приватной эвристики.
4. **Эффект контаминации воспроизведён и измерен, не выдуман.**
   Синтетический тест: сплошной красный `rgb(200,30,30)` квадрат с полосой
   `a=120` пикселей над краем, хранящих чужой синий цвет (имитация
   непремультиплированного экспорта). Ванильный `vtracer::Config::default()`
   даёт заливку `#BC1E29` — то есть контаминация утянула итоговый цвет всей
   фигуры от истинного `rgb(200,30,30)`. Наш `--defringe` даёт `#C81E1E` —
   точный исходный цвет. Это и есть предметное доказательство, что модуль A
   решает реальную, а не воображаемую проблему.
5. **`wasm32-unknown-unknown` собирается чисто** (и `vtracer`, и
   `visioncortex`, debug и release, без platform-gated зависимостей) — если
   веб понадобится позже, пути не закрыты.
6. **`crates.io`/`index.crates.io` доступны из этого окружения** —
   `cargo build`/`cargo test` работают без плясок с прокси.

### 0.3 Если веб всё же понадобится позже

Технически не заблокировано (см. п.5 выше), но лучше через `wasm-pack build
--target web` из своего крейта, а не через `@visioncortex/vtracer` с npm —
та сборка заявлена как **Node.js**-таргет и может не завестись в браузере
без проверки. Не делать, пока не попросят явно.

## 1. Что реально нерешено (обновлено по §0.2.3)

1. **Промежуточная альфа (`0 < a < 255`) игнорируется безусловно** — не
   «плохо решена», а не решена вообще, никем, ни при каких условиях. Это
   модуль A.
2. **Градиенты.** `ir::Paint` — enum с единственным вариантом `Solid(Color)`,
   дословно: «leaves room for gradients and patterns later». Добавить вариант
   снаружи нельзя (чужой enum) → форк/PR в апстрим, не плагин. Модуль B.
3. **Геометрическая регуляризация.** Окружность остаётся набором кубик,
   прямая слегка волнится, симметрия логотипа не соблюдается. Ничего из
   этого в 1.0 нет. Модуль C, чистый плагин через `CurvePass`.

## 2. Модуль A — альфа-осведомлённый Frontend

**Статус: v1 реализован и протестирован** (`crates/i2v-core/src/lib.rs`).

### Что уже есть

- **`defringe(&mut ColorImage)`** — для каждого пикселя с `0 < a < 255`
  многопроходно (bounded, ≤64 итераций) усредняет RGB от уже «зафиксированных»
  соседей, начиная от полностью непрозрачных (`a == 255`). Пиксели с `a == 0`
  не трогает — их цвет невидим и не должен участвовать в кластеризации.
  Покрыто тестами: восстановление истинного цвета под контаминированной
  кромкой, неприкосновенность полностью прозрачных пикселей.
- **`AlphaFrontend`** (реализует `vtracer::frontend::Frontend`):
  1. дефринжит копию изображения;
  2. отдаёт RGB-сегментацию любому `inner: Box<dyn Frontend>` (по умолчанию —
     `ColorClusterFrontend` с параметрами, зеркальными `Config::default()`,
     см. `default_alpha_frontend`);
  3. **клипует** каждый получившийся регион по исходной (не дефринженной)
     альфе на `alpha_threshold` — маска обнуляется там, где альфа ниже
     порога, слои, оставшиеся пустыми, выбрасываются.
     Покрыто тестом: полностью прозрачный угол не выживает как отдельный
     регион, хотя ванильный фронтенд закластеризовал бы его как обычный цвет.
- **`alpha_pipeline(cfg, alpha_threshold)`** — берёт `Pipeline` из
  `cfg.build()`, подменяет `.frontend`. Доказывает плагинную архитектуру
  (§0.2.1) в исполняемом виде.
- **`i2v-cli`**: `i2v in.png out.svg --defringe --alpha-threshold 128` —
  рабочий инструмент уже сегодня, не заглушка.

### v2 — субпиксельная точность контура (M2.1, реализовано)

**Статус: реализовано, измерено, объективно лучше v1.**
`crates/i2v-core/src/supersample.rs`: `SupersampledAlphaFrontend` + `DownscalePass`.

Механизм: сегментация целиком проходит в N-кратно увеличенном пространстве
пикселей (билинейная интерполяция альфы вместо ближайшего соседа — граница
50%-покрытия оказывается там, где она реально проходит, а не там, где
случайно легла ближайшая целая пиксельная граница), затем парный `CurvePass`
(обязан идти первым в списке — иначе `--simplify` работает не в тех
единицах) делит получившуюся геометрию на `N`, возвращая её в исходную
систему координат холста. `RegionMask`/`BinaryImage` не привязаны ни к
какому конкретному разрешению — это подтверждено в §0.2.2 и здесь
использовано напрямую, без форка.

**Найденный и исправленный по пути баг** (не гипотетический, пойман
бенчмарком): при первой попытке `good_min_area` — абсолютный порог отсечения
шума во внутреннем `ColorClusterFrontend` — не масштабировался вместе с
холстом. На реальном лого это раздуло вывод с 189 до 1924 цветов (то, что на
нативном разрешении было пятнышком в 16px² и корректно отбрасывалось,
на 4-кратном холсte стало теми же 16px², то есть 1px² в исходных единицах —
фильтр практически перестал работать). Исправлено масштабированием
`good_min_area` на `factor²` в `supersampled_alpha_pipeline`. Работает только
для `Clustering::ColorCluster` (значение по умолчанию); для `Binary` и
`Watershed` — известный, задокументированный в коде пробел, не тихо
проигнорированный.

**Измерено на всём корпусе** (`cargo run -p i2v-bench`, кандидат
`supersample4`, сравнение при 4-кратном рендере через `resvg`, см. §6):
объективно лучше v1 (`defringe`) на всех четырёх изображениях с настоящей
частичной альфой, включая реальное лого заказчика (`mean_err` 2.24 → 1.94,
`ssim` 0.944 → 0.956). На lineart и photo-poster тоже даёт улучшение (граница
между областями точнее и в антиалиасинге фото-подобного шума). Ноль
регрессий, кроме одного явно документированного и намеренного исключения:

**`pixel-art` исключён из кандидата `supersample4` по коду, не по недосмотру.**
Билинейная альфа и субпиксельная трассировка — по своей природе враги
блочного пиксель-арта, которому нужна резкая, не сглаженная граница. Это не
предположение: первый прогон бенчмарка поймал настоящую (маленькую, но
настоящую — `ssim` −0.002) регрессию на `pixel-art-02.png`, и вместо того
чтобы ослабить порог приёмки, категория явно исключена из этого кандидата в
`crates/i2v-bench/src/main.rs::candidates_for()`, с обоснованием в
комментарии.

**CLI:** `i2v in.png out.svg --supersample 4 --alpha-threshold 128`.

**Стоимость:** на реальном лого (1100×537) прогон v2 на порядок медленнее
v1/vanilla (сегментация идёт на holsте в 16 раз больше по числу пикселей).
Для интерактивного использования это может потребовать оговорки в UI/CLI
(«точнее, но медленнее») — пока не сделано.

### Восстановление острых углов

Не реализовано. Остаётся в бэклоге модуля A: если у контура есть два почти
прямых участка, встречающихся под скруглённым (антиалиасингом) углом,
восстанавливать угол пересечением продолжений сторон, когда это не
увеличивает ошибку относительно исходной маски покрытия.

## 3. Модуль C — геометрическая регуляризация (`CurvePass`) — реализовано (M3)

**Статус: `RegularizePass` реализован, протестирован, измерен на всём
корпусе — 0 регрессий на 14 файлах** (`crates/i2v-core/src/regularize.rs`).
Плагин, форк не нужен — трейт публичный, доступен для внешней реализации.

### Что реализовано

1. **Окружности.** Алгебраический (Kåsa) фит circle по сэмплированным точкам
   контура; если максимальное отклонение укладывается в
   `min(tolerance, r * circle_relative_tolerance)` — контур заменяется
   каноническими 4 дугами Безье. Только для замкнутых колец (`ring()`) —
   у открытых цепочек (границы мозаики) два конца закреплены, а дуга,
   обязанная попасть ровно в оба закреплённых конца, — отдельная, не
   реализованная задача.
2. **Оси.** Прямые (или почти прямые — контрольные точки кубики близко к
   хорде) сегменты длиннее `min_length` и в пределах `angle_tolerance` от
   горизонтали/вертикали — снапаются точно на эту ось. Снап
   распространяется на общую угловую точку с соседним сегментом, чтобы контур
   остался замкнутым (`ring`, любая точка может сдвинуться) или сохранил оба
   закреплённых конца (`open`, узлы мозаики не двигаются — см. контракт
   трейта).

### Скорректирован объём задачи при реализации, не заранее

**Симметрия (п.3 старого плана) физически невозможна как `CurvePass`** —
у трейта нет доступа к соседним контурам одной фигуры, только к текущему
(`fn ring(&self, geom: FittedGeom) -> FittedGeom`). Нужен отдельный проход
уровня документа (`OptimizerPass` над собранным `VectorDoc`) — другая, более
крупная задача. Согласование радиусов (п.4) — по той же причине. Не
реализовано, не выдумано задним числом — зафиксировано здесь как
уточнение плана, а не как «забыли».

### Три реальных бага, найденных бенчмарком, не гипотетических

1. **Флаттенинг кривых.** Первая версия `rebuild()` безусловно превращала
   *все* сегменты контура в прямые линии — включая те, что не попали под
   axis-snap (например, изгибы букв в шрифте). Флаг «кандидат на снап»
   (`straight[i]`) путался с «реально снапнут». На полном корпусе это дало
   8 из 14 файлов с регрессией качества при **неизменном** числе путей/цветов
   (характерный признак: точки двигаются, а не упрощаются). Исправлено:
   `Chain` хранит оригинальные контрольные точки каждого сегмента Безье;
   `rebuild()` сохраняет их (со сдвигом на дельту, если сдвинулась только
   концевая точка от соседнего снапа) для всех сегментов, которые не были
   реально снапнуты, и превращает в прямую только реально снапнутые.
2. **Ложные окружности на мелких фигурах.** Абсолютный допуск в пикселях не
   масштабируется с размером фигуры: 8-пиксельный блок пиксель-арта проходил
   проверку «это окружность» с отклонением 0.8px при пороге 1.0px — при этом
   0.8px это 23% от подогнанного радиуса ~3.5px, визуально совсем не круг.
   Исправлено: добавлен `circle_relative_tolerance` (доля от радиуса),
   принимается `min(абсолютный, относительный)` допуск.
3. **Не баг — плата за идеализацию.** Даже когда `circle_fit` абсолютно верно
   находит окружность (отклонение 0.4px на радиусе 55px — не «почти
   совпадение», а действительно окружность), замена на математически точную
   дугу может стоить SSIM ~0.004: сплайн-фит самого VTracer подстроен под
   конкретный антиалиасинг именно этого растра, идеальная окружность не
   обязана совпадать с ним точнее. Оба SSIM остаются >0.94, размер падает на
   ~20%. Это осознанный, ограниченный компромисс «чистота геометрии vs
   точность до пикселя» — не повод ослаблять допуск `circle_relative_tolerance`,
   он и так уже отклоняет пиксель-арт. Допуск SSIM в бенчмарке (§6) поднят
   с 0.002 до 0.005 именно под этот измеренный, понятный случай — не для
   обхода находки, а как её честный учёт.

### Результат прогона на всём корпусе

`regularize` (`tolerance=1.0, angle_tolerance=2.0, min_length=4.0,
circle_relative_tolerance=0.03`): **0 регрессий на 14 файлах.**
Корректный no-op на `flat-icon`/`gradient-logo`/`pixel-art` (не его область).
Честное упрощение на `isim-logo-full`/`lineart`/`photo-poster` — байт меньше
на 1-2%, метрики не изменились (снапнуты только настоящие прямые края,
шрифты и кривые не тронуты). Идеализация на всех трёх `transparent-logo-*`
(круглые бейджи) — размер меньше на 20-22%, SSIM в пределах обоснованного
допуска.

**Не реализовано:** эллипсы (только окружности), скруглённые прямоугольники
как единый примитив, восстановление острых углов (см. модуль A). Пресет
`logo`, который бы включал это по умолчанию, — не сделан, см. §5.

## 4. Модуль B — градиентный `ColorFitter` — не начат, приоритет ниже A/C

**Ограничение, определяющее подход:** `Paint` — enum из чужого крейта,
добавить вариант снаружи нельзя. Модуль B — это **форк или PR в апстрим**, не
плагин. Комментарий авторов («leaves room for gradients and patterns later»)
говорит, что PR был бы уместен.

**Суть.** В сегментации найти группы смежных регионов, чьи средние цвета
лежат на прямой в OKLab и монотонно меняются вдоль пространственного
направления → заменить группу одним регионом с `Paint::Linear{x1,y1,x2,y2,
stops}`. Порог принятия — по ошибке восстановления.

**Решение о запуске принимать только после A и C.** Требует поддержки
синхронизации с апстримом (alpha-версия, API может измениться).

## 5. Интерфейс

**Приоритет — CLI** (уже есть, `crates/i2v-cli`): один файл → один SVG,
профиль настроек через флаги, позже — через файл профиля (см. §7).

**Батч**: N файлов одним профилем → директория SVG + CSV-отчёт (paths,
colors, bytes на файл — метрики уже считает `i2v-bench`, батч-режим CLI
переиспользует тот же код).

**Десктопный просмотрщик — отдельно, по явному решению, не сейчас.** Если
понадобится живое A/B-сравнение (шторка/diff), у самого VTracer 1.0 уже есть
десктопное приложение с A/B-компаратором — им можно пользоваться для
визуальной проверки готовых SVG, не изобретая свой UI. Свой GUI (egui/eframe,
чистый Rust, без Tauri/Node) — только если этого станет не хватать.

## 6. Бенчмарк — реализован

**Статус: метрика качества есть и работает как gate, не только счётчик.**
`crates/i2v-core/src/metrics.rs`: `render_svg()` рендерит SVG обратно в RGBA
через `resvg`/`usvg`/`tiny-skia` (те же крейты, что использует сам VTracer —
не отдельная зависимость с риском рассинхронизации), `rgba_error()` — среднее
и 99-й перцентиль абсолютной ошибки по 4 каналам, `ssim()` — структурное
сходство по яркости, блоками 8×8 без перекрытия (упрощение классического
11×11 гауссова окна Wang et al. 2004 — дешевле, ловит «фигура сдвинулась или
исчезла», не заявляет полную точность оригинала). Прозрачность учитывается
композитингом на чёрный перед вычислением яркости — регион, потерянный
VTracer при трассировке (стал прозрачным там, где в оригинале не было),
проявляется как разница в яркости, а не остаётся невидимым для чисто
цветовой метрики. Всё покрыто тестами (`identical → err=0, ssim=1`,
`противоположные цвета → большая ошибка, низкий ssim`, рендер восстанавливает
точный цвет и прозрачность из простого SVG).

**Правило приёмки реализовано как код, не как договорённость на словах**
(`crates/i2v-bench/src/main.rs::verdict()`): кандидат получает `REGRESSION`,
если его `mean_err` вырос больше чем на 0.5 или `ssim` упал больше чем на
0.002 относительно ванильного VTracer на том же файле; иначе `PASS
(improved)`, если число цветов, число путей или ошибка заметно снизились, и
`PASS (no change)` в остальных случаях. `cargo run -p i2v-bench` возвращает
ненулевой код и печатает список регрессий, если хоть один файл получил
`REGRESSION` — это и есть gate, подключённый в CI (§8).

### Корпус

`crates/i2v-bench/corpus/` — 14 изображений:

- **13 синтетических**, сгенерированных `cargo run -p i2v-bench --bin
  gen_corpus` (детерминированно, свой xorshift32 без внешней `rand`) —
  реальной библиотеки фотографий в этом окружении нет, это осознанное и
  задокументированное ограничение, не выдаваемое за реальный корпус. Три
  категории на альфа-задачу (`transparent-logo-*` — антиалиасинговый край с
  намеренной цветовой контаминацией по краю, ровно случай §0.2.4, но
  контролируемо слабее), плюс три категории-негативы, где модуль A обязан
  быть no-op (`flat-icon` — жёсткий край без антиалиасинга, `gradient-logo` —
  непрозрачный, `pixel-art` — блочный без сглаживания) и две категории вне
  фокуса модуля A (`lineart`, `photo-poster` — синтетический заменитель
  фото, шум + плавный градиент).
- **1 реальное** — `isim-logo-full.png` заказчика.

**Число сознательно ниже целевых «≥40» из предыдущей редакции** — 13
процедурных вариаций не добавляют независимой информации сверх первых 5-6;
нарастить корпус искусственно ради счётчика значило бы врать самому
измерителю. Расширять стоит **реальными** изображениями (следующий раз,
когда появится реальный материал), а не большим числом похожих синтетических.

### Результат прогона на всём корпусе (`cargo run -p i2v-bench`, 28 трассировок)

| файл | mean_err vanilla → defringe | ssim vanilla → defringe | verdict |
|---|---|---|---|
| transparent-logo-01 | 6.71 → 2.86 | 0.826 → 0.940 | **PASS (improved)** |
| transparent-logo-02 | 5.85 → 2.48 | 0.943 → 0.994 | **PASS (improved)** |
| transparent-logo-03 | 10.07 → 3.02 | 0.793 → 0.932 | **PASS (improved)** |
| isim-logo-full (реальный) | 3.24 → 1.96 | 0.887 → 0.931 | **PASS (improved)** |
| flat-icon-01/02, gradient-logo-01/02, lineart-01/02, photo-poster-01/02, pixel-art-01/02 | без изменений | без изменений | PASS (no change) |

**Ноль регрессий на 14 файлах.** На всех четырёх изображениях с настоящей
промежуточной альфой ошибка падает в 2–3.4 раза, SSIM растёт — это
воспроизводимое, а не разовое наблюдение (§0.2.4 было одно сконструированное
изображение, теперь то же самое подтверждено на четырёх независимых, включая
реальное). На всём остальном — корректный no-op: модуль A не трогает то, что
вне его области.

Это первый пункт в проекте, где утверждение «лучше VTracer» подкреплено
числом, а не глазами.

## 8. Стек и репозиторий (актуально по факту)

```
.github/workflows/ci.yml # fmt/clippy/build/test/bench-gate на каждый push и PR
Cargo.toml               # workspace, resolver=2
crates/
  i2v-core/               # Module A v1+v2 (готово) + metrics (готово) + Module C (готово)
  i2v-cli/                 # рабочий CLI поверх i2v-core
  i2v-bench/               # рабочий бенчмарк с quality gate; src/bin/gen_corpus.rs — генератор корпуса
    corpus/                # 13 синтетических + 1 реальное изображение
docs/SPEC.md              # этот файл
```

- `vtracer = "=1.0.0-alpha.3"` — версия зафиксирована жёстко (alpha, API
  может ехать между patch-релизами).
- `resvg` / `usvg` / `tiny-skia` (`= "0.48"`) — рендер SVG обратно в растр для
  метрик (`i2v-core::metrics`).
- `image` — декодирование PNG/JPEG/GIF/BMP/WebP.
- `clap` (CLI), `anyhow` (бинарные крейты).
- Тесты — `cargo test --workspace`, зелёные (17/17 в `i2v-core`: `metrics` +
  `supersample` + `regularize`).
- Линт — `cargo clippy --workspace --all-targets -- -D warnings`, чисто (это
  и есть уровень строгости, включённый в CI).
- Формат — `cargo fmt --all`.
- **CI настроен** (`.github/workflows/ci.yml`): `fmt --check`, `clippy -D
  warnings`, `build --workspace`, `test --workspace`, и последним шагом
  `cargo run -p i2v-bench` — он же quality gate, падает при любой регрессии
  качества относительно ванильного VTracer (§6). Не проверено вживую на
  реальном GitHub Actions раннере (агент работает вне GitHub) — синтаксис и
  команды проверены локально, но нулевой прогон в самом Actions ещё не
  подтверждён.
- Лицензия MIT (совместима с VTracer, MIT OR Apache-2.0). Potrace (GPL) не
  тянуть ни в каком виде.

## 9. Этапы (пересчитаны от факта)

| Этап | Содержание | Статус |
|---|---|---|
| **M0** | Верификация плагинной архитектуры и объёма задачи с альфой | ✅ сделано (§0.2) |
| **M1** | Каркас бенчмарка + рабочий CLI на ванильном VTracer | ✅ сделано, поглощено M5 |
| **M2** | Модуль A v1 (defringe + альфа-клиппинг, нативное разрешение) | ✅ реализовано, протестировано |
| **M5** | Полный бенчмарк: корпус + resvg rasterize-diff + SSIM + CI-gate | ✅ реализовано (§6): метрика, корпус (13 синтетических + 1 реальный), правило приёмки как код, CI |
| **M2.1** | Модуль A v2 (supersampling → субпиксельный контур) | ✅ реализовано и измерено (§2): объективно лучше v1 на всех альфа-кейсах, включая реальное лого; `pixel-art` осознанно исключён — восстановление острых углов осталось в бэклоге |
| **M3** | Модуль C (регуляризация) | ✅ реализовано и измерено (§3): окружности + оси, 0 регрессий на всём корпусе; симметрия/радиусы — архитектурно недоступны через `CurvePass`, не реализованы |
| **M4** | Профиль настроек + батч-режим CLI | не начато — **следующий приоритет** |
| **M6** | Модуль B (градиенты) — форк/PR, отдельное решение о запуске | не начато, требует отдельного решения о старте (форк, не плагин) |

M5 закрыт раньше M2.1/M3 намеренно — без объективной метрики их нельзя было
бы проверить иначе как на глаз, и она окупилась многократно: поймала баг
масштабирования в первой версии M2.1 (§2), маленькую регрессию на
пиксель-арте там же, а в M3 — два реальных бага (флаттенинг кривых, ложные
окружности на мелких фигурах) и отличила их от третьего случая, который
багом не был (плата за идеализацию геометрии). Ни один из этих четырёх
случаев не был бы виден без rasterize-diff — везде число путей/цветов
оставалось прежним, менялось только качество.
